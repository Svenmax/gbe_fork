# GC Verification And Build Entry Points

This document records the build and verification paths that matter for Dota GC refactor work.

## Source Entrypoints

| Entrypoint | Role | GC Source Inclusion Rule |
| --- | --- | --- |
| `premake5.lua` production projects | Production builds for regular/experimental API and steamclient targets | `common_files` includes `dll/**`, so new production `dll/*.cpp` files are included unless a target-specific `removefiles` rule excludes them |
| `tools/run_gc_offline_tests.sh` | Local Linux offline GC compile/run harness | Each test binary lists exact `.cpp` files; new production helper `.cpp` files must be added to every affected test binary |
| `premake5.lua` always-on GC utility tests | Optional tool targets generated by default | GC replay/message/config/wire/custom-game/lobby-flow/lobby-state test targets are declared outside `--with-gc-tests` |
| `premake5.lua --with-gc-tests` | Optional heavy handler/payload test generation | Handler and payload helper tests are only generated when this option is set |
| `.github/workflows/emu-build-all-linux.yml` | Production Linux build matrix | Runs production/tool matrix generation; it does not pass `--with-gc-tests` |
| `.github/workflows/emu-build-all-win.yml` | Production Windows build matrix | Runs production matrix generation; it does not pass `--with-gc-tests` |
| `.github/workflows/emu-pull-request.yml` | PR gate | Runs Windows API release build and `tools/run_gc_verification.sh --fast` on Linux |

## New File Placement Rules

- New production GC `.cpp` files under `dll/` enter production Premake builds automatically through `common_files`.
- New production GC `.cpp` files must be manually added to `tools/run_gc_offline_tests.sh` for each offline binary that needs the symbol.
- New production GC `.cpp` files used by optional Premake test targets must be manually added to the matching `files {}` list in `premake5.lua`.
- New handler or payload test-only `.cpp` files must stay out of production targets; add them only to `tools/run_gc_offline_tests.sh` and the `--with-gc-tests` Premake block.
- New headers used by optional Premake test targets should be listed in `premake5.lua` for IDE/project visibility even when compilation would work through includes.

## Verification Gates

Use the fast gate for small parser/helper/handler changes while iterating:

```bash
tools/run_gc_verification.sh --fast
```

Expected coverage:

- Core GC message utility tests
- GC config tests
- Proto wire tests
- High-signal replay fixtures
- Payload helper tests
- Handler smoke tests
- Refactor audit
- `git diff --check`

Use the full gate before handing off completed GC refactor work:

```bash
tools/run_gc_verification.sh --full
```

Expected additional coverage:

- Chat channel replay fixture
- Lobby lifecycle replay fixture
- Wire edge-case replay fixture
- Dota lobby flow focused tests
- Dota lobby state focused tests
- Dota custom game focused tests

The wrapper preserves `tools/run_gc_offline_tests.sh` as the primary offline test entry point and adds audit/style orchestration around it.

## Audit Gate

`tools/_audit_gc_refactor.py` checks structural guardrails:

- Header declarations have matching definitions.
- Shared free-function definitions have declarations.
- `REFACTOR_TODO.md` line references remain accurate where applicable.
- Post-login dispatch table mappings stay aligned with expected handlers.
- Template blob ownership stays in approved files.
- New production helper `.cpp` files are included in offline/Premake test source lists.
- High-risk handler side effects stay behind approved seams or explicit baselines.
- High-risk reason strings remain documented in `docs/gc/reason-trace-governance.md` and covered by tests/specs.

## Premake Gate

Use this when build files, project configuration, or compile-unit membership changes:

```bash
./premake5 --with-gc-tests gmake2
```

Then build the generated target for the affected platform/toolchain when available. This gate is optional for logic-only refactors that only touch files already compiled by `tools/run_gc_verification.sh --full`.

## Platform Notes

| Risk | Linux Path | Windows Path | Mitigation |
| --- | --- | --- | --- |
| Project generator action | `gmake` | `vs2026` | Keep source lists in `premake5.lua`, not generated project files |
| Production source inclusion | `common_files` + target `removefiles` | `common_files` + target `removefiles` | Production GC files should live under `dll/` and avoid OS assumptions |
| Offline GC verification | Shell tests use local C++ compiler | No equivalent shell workflow | Treat shell offline tests as Linux gate; use Premake `--with-gc-tests` for generated project coverage |
| Include order | Shell tests pass explicit `-I. -Isdk -Ilibs` | Premake targets inherit project include dirs and generated proto dirs | Add source dependencies explicitly to shell and Premake test targets |
| Link order | Shell tests link direct source files in command order | Premake compiles project source set | Keep helper code free of hidden link-only dependencies |
